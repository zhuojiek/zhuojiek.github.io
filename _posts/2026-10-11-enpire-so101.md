ENPIRE is a reset-execute-verify-refine harness for code-as-policy, robot tools, and real-world RL. It's built around a bimanual YAM station, and I don't have one. I do have [clanker](/posts/2026/09/21), a 3D-printed SO-101, so I ported the arm-level stack over to it. The code is on the `so101-port` branch of [my fork](https://github.com/shimamooo/ENPIRE-so101/tree/so101-port).

The two arms are pretty different:

| | YAM | SO-101 |
|---|---|---|
| Arm joints | 6 | 5 |
| Motors | DaMiao over CAN, impedance control | Feetech STS3215 over USB serial, position control |
| Gains | `kp`/`kd` per command | Ignored, the servos run their own position loop |
| Force estimate, gravity comp | Yes | No |
| Arms per station | 2 | 1 |

The goal was for the rest of ENPIRE to see an SO-101 as just another arm, without changing any of the YAM code.

## 1. Kinematics

First I needed a model of the arm. TheRobotStudio's SO-ARM100 repo has an MJCF for the SO-101, so I vendored the kinematic tree from `so101_new_calib.xml`, removed the meshes, and renamed the gripper frame to `gripper_site`. Joint zeros follow LeRobot's degrees calibration, where each joint reads zero at the middle of its range.

Forward kinematics is just MuJoCo. For inverse kinematics I used `mink`, which solves a small QP each step for joint velocities that move the end-effector toward a target frame, subject to joint limits.

The catch is that the SO-101 only has 5 arm joints, so most 6D pose targets are unreachable. If you weight position and orientation equally, the solver compromises on both and you end up somewhere you didn't ask for. So the IK weights position at 1.0 and orientation at 0.1, supports a position-only solve, and returns the residual position and orientation errors. That way the caller can check whether the solution is actually good before commanding it.

## 2. Robot profile

ENPIRE describes each robot with a `RobotProfile`: joint limits, home pose, gripper range, end-effector frame, control frequency, and cameras. `so101_profile` fills this in for a single arm at 30 Hz with no cameras. It also sets interpolation gains, but those only shape tracking in simulation. The real servos ignore them.

## 3. Driver

LeRobot already has a Feetech driver for the SO-101, so `So101Robot` wraps it instead of talking to the servos directly. Most of the work is unit conversion: LeRobot uses degrees and a 0–100 gripper, while ENPIRE uses radians and a 0–1 gripper with 0 closed. All conversion happens in this one file, and commands outside the joint limits get clipped.

`So101Robot` exposes the same methods as `YamRobot`. It accepts `kp` and `kd` but ignores them, since the STS3215 servos only run their internal position loop.

Two more things:

- **Calibration.** LeRobot normally prompts you to calibrate when you connect. ENPIRE never runs that interactive flow. You calibrate each arm once with `lerobot-calibrate`, and the driver connects with `calibrate=False`, writes the stored calibration to the motors if they disagree, or errors out with the exact command to run if no calibration file exists.
- **Leader arm.** `So101LeaderArm` reads a second SO-101 through LeRobot's leader teleoperator. Its `get_info` matches the YAM leader RPC, except that the SO-101 leader has no buttons, so that part is always empty.

## 4. Arm server

On a YAM station each arm runs behind a `portal` RPC server, and the rest of ENPIRE talks to it through `FollowerRobotClient`. I wrote an SO-101 arm server that binds the same RPC names, so `FollowerRobotClient` drives an SO-101 with no changes. The follower runs on port 11337, and `--mode leader` serves the leader arm on 11338 for teleop.

The server has a `--dry-run` that prints the resolved config without opening the serial port, and a `--max-relative-target` flag that caps how far each command can move a joint, in degrees. I'd recommend 5 for first runs.

## 5. Environment

`RealSo101Env` covers the arm API of `RealYamEnv`. Observations come back as joint positions, gripper position, and the end-effector pose from forward kinematics. Beyond raw joint commands it has `move_to_joint_pos`, which linearly interpolates to a target under a max joint velocity, plus `go_home` and `set_gripper`.

One subtle detail is in `set_gripper`. The obvious approach is to read the arm's measured position, change the gripper value, and send it back. But the servos sag a little under gravity, so the measured position sits slightly below the target. Every gripper call would then command the arm a bit lower than before, and it would slowly creep downward. So `set_gripper` holds the last *commanded* arm target instead.

## 6. Dependencies

Everything lives behind a `control-so101` extra, so SO-101 stations skip the DaMiao CAN stack. LeRobot 0.5 needs Python 3.12, so the extra pins LeRobot 0.4. That version pins an older `huggingface-hub` than the local vision extra, so I declared the two extras as conflicting in `uv`.

## Testing

All of this is tested against fake LeRobot devices, so the 28 tests run without hardware. They cover kinematics round-trips, unit conversion, the calibration paths, the RPC surface of the arm server, the profile, and the environment.

## What's next

This only covers the arm. Cameras, grasp planning, cuRobo, and the real-world RL stack all still assume a YAM station, so those come next. After that I want to run actual ENPIRE tasks on clanker.
